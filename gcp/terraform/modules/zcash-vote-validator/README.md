# zcash-vote-validator

Provisions a GCE host to run a validator on Valar Group's Shielded-Vote chain
(`zvote-1`), as documented at <https://setup.valargroup.org/>.

The module prepares the host. It does **not** join the chain. Joining runs
Valar Group's `join.sh` interactively, once, by an operator. Everything on either
side of that step — disk, user, `rage`, firewall, systemd hardening, encrypted
key backup, disk snapshots, and an operator CLI — is automated here.

## Why the join is manual

`join.sh` is not safe to run from a startup script:

- It begins with an unconditional `rm -rf "$SVOTE_HOME"`. A GCE startup script
  re-runs on every boot, so wiring it in would destroy the validator's signing
  key the first time the instance restarted.
- It prompts for a validator name on `/dev/tty` and hard-fails when it detects an
  existing install non-interactively.
- The result needs a human anyway: registration puts you in a queue, and a Valar
  Group admin has to approve and fund the operator address out of band.

`svote join` wraps it: presets the environment, checks the installer's SHA-256,
refuses to clobber an existing validator, and handles registration recording,
snapshot enablement and the key-backup prompt afterwards.

See [`docs/svote-installer-security-analysis.md`](../../../docs/svote-installer-security-analysis.md)
for a full review of what the installer trusts.

## What gets deployed

| | |
|---|---|
| Instance | `e2-standard-4` (4 vCPU / 16 GB; upstream asks for 4 vCPU / 8 GB) |
| Boot disk | 20 GB `pd-balanced` |
| Data disk | 120 GB `pd-ssd` mounted at `/var/lib/svote`, which is also the `svote` user's home, so `SVOTE_HOME=/var/lib/svote/.svoted` |
| Addresses | reserved external (public URL, cert name, peer address) + internal |
| Ingress | `22` from IAP only, `80`/`443` and `26656` from anywhere |
| Service | `svoted.service`, generated by the installer, plus a hardening drop-in staged by this module |
| Timers | `svote-backup-keys.timer`, `svote-snapshot.timer` — both installed disabled, enabled after the join |

A public IP is not optional: the chain only treats a validator as client-ready
once its helper API answers over public HTTPS, and Let's Encrypt has to reach
`:80` for Caddy to get a certificate.

## Bootstrap

```bash
# 1. Generate the backup key OFF the VM and keep the identity file safe.
rage-keygen -o svote-backup-identity.txt
#   Public key: age1... <- this is the recipient

# 2. Configure and apply.
cd gcp/terraform
source gcloud.env
```

```hcl
vote_validator_enabled                  = true
vote_validator_key_backup_age_recipient = "age1..."   # from step 1
# vote_validator_tls_domain             = "svote.example.org"  # optional; see below
# vote_validator_join_script_sha256     = "..."                # optional; see below
```

```bash
tofu apply
tofu output -raw vote_validator_post_deployment_instructions
```

Then join, interactively — `-t` matters, the installer needs a terminal:

```bash
gcloud compute ssh zcash-vote-validator-0 --tunnel-through-iap \
  --zone "$TF_VAR_zone" -- -t 'sudo -iu svote svote join'
```

It asks for a validator name, installs `svoted`, syncs from a published
snapshot, registers with the join queue, offers to back up the signing key
(say yes), and prints the message to send to the Valar Group admin. Once they
approve and fund the operator address, the upstream wrapper bonds the validator
by itself.

## Operator CLI

Available as `svote` on the instance. Run as `svote` or root; it re-execs itself
as the `svote` user when needed.

| Command | |
|---|---|
| `svote join [--force]` | Interactive join. Refuses to overwrite an existing validator; `--force` backs the keys up and demands a typed `RESET` first |
| `svote addr` | Re-print the approval message for the voting admin |
| `svote status` | Network, moniker, height, `catching_up` |
| `svote bonded` | On-chain bonding status |
| `svote logs` | `journalctl -u svoted -f` |
| `svote backup-keys` | Encrypt and upload key material now; enables the timer on first success |
| `svote restore-keys` | Print the off-host restore procedure |
| `svote snapshot-now` | Snapshot the data disk now |
| `svote reset-snapshot` | Re-sync chain state from a published snapshot (backs keys up first) |
| `svote prestage-upgrade TAG` | Stage a coordinated upgrade binary |
| `svote remove` | Tear the validator down (backs keys up first) |

Every interactive login prints the validator's state, and nags until the signing
key has actually been backed up.

## Key backup

The validator's identity is created on the box by `svoted init-validator-keys`
and exists nowhere else. Upstream tells you to back it up and automates nothing.
This module automates it:

- `svote-backup-keys` tars `config/priv_validator_key.json`,
  `config/node_key.json`, `keyring-test/` and any `pallas.*` / `ea.*`, pipes it
  through `rage -r <recipient>`, and uploads to
  `gs://<project>-svote-keys/<instance>/` as a timestamped object plus
  `latest.tar.age`, each with a `.sha256` sidecar.
- The bucket is versioned and keeps 20 non-current versions. The instance's
  service account holds **`objectCreator` only**, so a compromised validator can
  write backups but cannot read its own backup history — and could not decrypt it
  anyway, because the age identity is not on the host.
- It **fails closed**. No age recipient configured means no upload, not a
  plaintext upload.
- `data/priv_validator_state.json` is deliberately excluded: it changes every
  block, and restoring a stale copy invites double-signing.

Backup cannot be scheduled before the join, because the keys do not exist yet.
The timer ships disabled and is enabled by the first successful backup.

The bucket lives in the root configuration, not this module, so it survives
`tofu destroy` of the instance — that is the point of a backup. It is created
only when `vote_validator_enabled` is true, and carries
`lifecycle { prevent_destroy = true }`, so flipping that flag back to false
fails the plan rather than quietly deleting every key archive. Decommissioning a
validator is meant to be deliberate: take a final backup, verify you can decrypt
it off-host, then remove the lifecycle block or drop the bucket from state.

> **Rehearse the restore.** Run `svote restore-keys`, follow it end to end on a
> workstation holding the identity file, and diff the result against the live
> file. A backup you have never decrypted is not a backup.

> **One host, one key.** Restoring the signing key — or a data disk snapshot
> containing it — onto a second running host double-signs. Destroy or
> permanently stop the original first.

## TLS and the public URL

With `vote_validator_tls_domain` empty (the default) the module derives an
sslip.io hostname from the reserved external IP, e.g. `34-72-10-5.sslip.io`, and
passes it to the installer as an explicit domain. No DNS record is needed.

This deliberately avoids the installer's own auto mode, which asks `ifconfig.me`
for the public IP — that would let a third party influence which certificate the
validator requests.

For anything long-lived, set `vote_validator_tls_domain` to a hostname you
control with an A record pointing at the reserved IP. sslip.io discloses the IP
in the public URL and makes certificate renewal depend on a third-party wildcard
DNS service staying up.

## Pinning the installer

`join.sh` is fetched over HTTPS from a DigitalOcean Spaces bucket with no
signature. `svote join` always prints the digest it fetched. Set
`vote_validator_join_script_sha256` to make a mismatch fatal:

```bash
curl -fsSL https://shielded-vote.nyc3.digitaloceanspaces.com/join.sh | sha256sum
```

Expect to update it when upstream changes the installer — that is the point.

## Rebuilding onto existing state

`svote snapshot-now` and the daily timer label snapshots
`purpose=svote-state`, `chain-id=<id>`, `source-disk=<disk>`, retaining
`vote_validator_snapshot_retention_count` (default 7).

To rebuild, pass one to `vote_validator_data_disk_snapshot` and apply. The
snapshot contains the signing key, so the rebuilt host **replaces** the original.
`svote join` will refuse to run against the restored validator, which is correct.

There is no automatic `data.google_compute_snapshot` lookup for this module, on
purpose: it would make every plan fail until the first snapshot existed.

## Upgrades

`upgrade_mode` defaults to `cosmovisor`. The installer sets
`DAEMON_ALLOW_DOWNLOAD_BINARIES=false` and this module leaves it that way, so
pre-stage with `svote prestage-upgrade <tag>`. Enabling auto-download would let
chain governance run arbitrary binaries here, even with
`DAEMON_DOWNLOAD_MUST_HAVE_CHECKSUM=true`, because the checksum comes from the
governance proposal itself.

## Notes and known rough edges

- The `svote` account has passwordless sudo, because the installer requires it
  (`sudo tee` into `/etc/systemd/system`, `sudo apt-get`, `sudo systemctl`). That
  makes the account root-equivalent. It can be revoked once the validator is
  bonded; nothing in this module needs it afterwards except `svote`'s own
  `systemctl` calls.
- The installer generates `svoted.service` with `User=$(whoami)` and no hardening
  directives. Running it as `svote` is what keeps `svoted` off root; the
  `10-hardening.conf` drop-in is staged before the unit exists so it applies
  immediately and survives the installer rewriting the base unit.
- `rage` is installed from the `str4d/rage` GitHub release `.deb` because Debian
  does not package it. That resolves `/releases/latest`, so the version drifts
  between builds.
- The startup script is safe to re-run and does so on every boot, which is how
  updated operator tooling gets onto a running host. It never touches
  `$SVOTE_HOME`.
